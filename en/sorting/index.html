Sorting side by side

Twenty-five ways of putting a row in order, run one step at a time or several at once. The efficient ones, the deliberately terrible ones and the jokes all get the same row to work on.

The question
Given the same row, what actually differs between the algorithms? How many comparisons, and how many moves?
What you need first
Being able to say which of two values is larger, and having met the idea of repetition. Written for lower secondary upwards.
Predict before you run it
Give bubble sort and quicksort the same row. Which one makes more comparisons?
How to run it

Reset picks a brand new random row every time. Changing which algorithms are selected keeps the row as it is, so you can compare them on the same data.

There are two colour families. Blue means "only looked at" (◇ read, ▲ compared) — nothing changed. Vermilion means "actually moved" (⇄ swapped, ↺ reshuffled as a whole, ▼ written). Besides those, a purple P is the pivot, a green ✓ means the position is settled, a grey → means it left the row (not destroyed) and ✕ means it was removed. Bar height is the value. If you cannot tell the colours apart, these marks and the table below carry the same information.

    Things worth checking

    • Compare: select bubble sort and quicksort together and watch the comparison counts on the same row. Take the number of elements from 8 to 32 to 64 — what happens to the gap?
    • Explain: binary insertion sort makes far fewer comparisons but exactly as many swaps. Say in your own words why.
    • Transfer: counting sort never compares anything. So can you always use a sort that does not compare? If not, when can you not?

    Comparisons and swaps are counted separately. Start by keeping the two apart.

    Binary insertion sort finds the slot with a binary search. Finding it is cheap — but making room still means shifting everything after it, one at a time.

    Counting sort uses the value itself as the address to store at. That only works when the values are whole numbers and you know their range.

    In more detail
    Wording

    The same job — putting things in order — costs wildly different amounts of work depending on how you go about it. Only ever swapping with your neighbour gets very expensive as the row grows. Splitting the row in half and merging the halves grows much more gently. There are also ways that never compare anything at all, but those only work when the values are whole numbers in a range you already know.

    Any comparison-based sort needs Ω(n log n) comparisons in the worst case. Bubble, selection and insertion sort are O(n²); merge sort and heapsort are O(n log n) in the worst case; quicksort is O(n log n) on average and O(n²) at worst. Counting sort runs in O(n + k) and radix sort in O(d(n + k)); neither is bound by that lower bound, because they use the key itself as an address rather than comparing keys.

    For teachers

    The easy misreading: that one step takes the same time everywhere. The algorithms advance one step together, but a step means different work in each one — a single comparison, a single write, or shuffling the whole row. This is not a race. What it does compare honestly is counts.

    A short task (5–10 minutes): select bubble sort and quicksort, vary the number of elements and record the comparison counts. Tabulate how each count grows with n, and discuss.

    On the joke algorithms: Stalin sort and Thanos sort destroy elements. Bogosort may never finish. Miracle sort moves nothing at all. Intelligent design sort marks everything settled while the row is plainly not sorted. Use them to ask what makes a sort correct in the first place.

    Where this stops

    • It is not a speed comparison. Everything advances one step at a time, and a step is not the same amount of work in each algorithm. Nothing here is a measurement of real running time.
    • The values are 1 to n, each used once, in random order. No value ever repeats, so you cannot see here whether equal values keep their original order (stability). Every count in counting sort is 1.
    • Radix sort distributes by decimal digits. Negative numbers, decimals and text are out of scope.
    • Sleep sort is shown as an order, not as real elapsed time. Run against a real clock, close values are not guaranteed to come out in order.
    • Bogosort and bozo sort are capped at 7 elements and 60,000 steps, and may still not finish.
    • Stalin sort and Thanos sort lose elements. They do not rearrange anything.
    • Miracle sort and intelligent design sort do not sort. They are here as jokes.
    • Quantum bogosort "discards the universe" as a joke; nothing actually happens.
    • Quicksort always takes the rightmost element of the range as its pivot. Other pivot choices are out of scope.
    • A green ✓ means strictly "this position will not change again". It is not used for a stretch that merely happens to be in order and will move later, as in insertion sort — watch the staircase shape for that instead.
    • For bogosort, bozo sort and miracle sort the total number of steps is deliberately not shown. Revealing up front which step it ends on would destroy the very property that there is no guarantee it ends at all. The steps are generated in advance internally, but not displayed.
    • The working row for bucket sort does not draw lines between the buckets; the elements simply sit in the order they were poured in.
    • The name origins are short summaries of the commonly given explanations. They have not been checked against scholarly sources one by one.

    Known gaps

    • No check of learning outcomes has been carried out. This screen is a trial of the subject matter.
    • No testing on the target devices has been done yet.
    • At most 6 algorithms run at once. More than that has not been tried.
